The case

Device to portal, and back. The brief's constraints.

  • ~50,000 devices, ~400 tenants — and 8,000 of them at a single site.
  • Firmware is another team's. 12–18 months to reach most devices, and never all of them.
  • So many firmware versions send data at the same time, permanently.
  • Devices go quiet for hours or months, then reconnect and send everything they buffered.
  • Users still expect current state, and to act — restart, push config, open a session.

Disclaimers

Where I have interpreted the brief, and what this deliberately is not.

  • I designed what we would start with, not the end state. Normally I would keep most of this high-level and deep-dive piece by piece — through consultation, exploration and spikes with the people who own each constraint.
  • I deliver what was asked. I would not normally fix ownership and delegation up front, and I would not write a delivery plan for its own sake — only for contingency and mitigation.
  • The design is AI-first. The initial shape is mine; from there I let it overrule me on some things and held my ground on others. Both are logged, with what each acceptance cost.
  • The plan excludes process. No team formation, project setup or delay budget. It assumes an autonomous cross-functional team, and a shared testing framework that exists or can be enabled.
  • The two hours were not measured as instructed. With AI in the loop, focused work is not meaningfully measurable — and time between commits is not time spent on this problem, it is usually time spent on another.

What I had to assume

The brief describes the fleet, not how a device behaves. These assumptions carry the design.

  • The cloud cannot open a connection to a device. Every exchange starts at the device, so a command waits until the device next checks in.
  • Device clocks can be wrong, and some reset to 1970 after a power cut. So we decide which value is newest by the order it reached us.
  • A device deletes its buffered data when we answer 200. So we store the data safely before we answer, and our log is the only copy.
  • Every record has an id that stays the same when resent. So a resent record is recognised and skipped.
  • Commands are one person acting on one device — a few thousand a day across 50,000 devices.

At this size nothing here needs a distributed database. Choosing one would be the most expensive mistake available.

Ingest

  • We store each message and answer the device first. We process it afterwards.
  • A 200 response means the gateway has stored the message safely. It has not been processed yet.
  • The hard part is not volume. It is 8,000 devices at one site reconnecting at once.
  • A record we cannot read is set aside, and the records after it are processed as normal.
  • Firmware we have never seen is read as far as possible, never refused.

ADR-002A 200 response means the payload is stored safely. It has not been processed yet.

ADR-003A record we cannot read is set aside with its raw bytes, and processing continues.

ADR-004A per-tenant rate limit, sized by device count, protects tenants from each other; large backlog payloads use a separate catch-up lane.

State and freshness

  • The portal shows what each device last told us, not what is true right now.
  • Every value shows when it was measured, or when we received it if the device clock is wrong.
  • We decide which value is newest by the order it reached us, not by the device clock.
  • A value old firmware cannot report is shown as a dash, never as zero.

ADR-005The arrival sequence number we stamp decides which value is newest, never the device clock.

ADR-006The same fixed limits for every device. The age of every value is always shown next to the badge.

Commands

  • Clicking a button saves a request. The device collects it the next time it checks in.
  • A 202 response means the request is saved and queued, not that the device has done it.
  • Every request expires: restart 24 h, config 7 days, remote session 15 min.
  • Each ends Confirmed, Inferred or Unknown, and the portal shows the evidence.

ADR-007Every action, including opening a remote session, is saved, queued, collected at the next check-in, and expires.

ADR-008Confirmed: the device told us. Inferred: we saw the expected change, such as a new boot time. Unknown: no evidence.

What this design does badly

  • Once we answer 200, the device deletes its data, so our log is the only copy.
  • If our side stops working, the portal makes it look like the customers' devices are the problem.
  • Fixed limits show rarely-reporting devices as Delayed even when they are working normally.
  • On old firmware, most command results are Inferred or Unknown, not Confirmed.
  • A restart is sent once. If it is lost on the way, the user has to ask again.

Eight weeks

  • Storing incoming data safely is the one thing we cannot redo later.
  • Everything else can be fixed afterwards by reprocessing the stored data.
  • Restart is planned, but it is the first thing we cut if we fall behind.
  • Week 8 shows the path works end to end. It does not show that it scales.

Who owns what

  • Each engineer owns one area end to end, not one layer across all areas.
  • The senior owns receiving and storing data — the part we cannot redo.
  • The newest engineer owns the old-firmware parsers: bounded, testable, and a fast way to learn the domain.
  • I keep the agreed data formats between areas, and the wording the portal shows users.
  • I hand over the most interesting problem, because keeping it would make me the bottleneck.

DEL-008The format the parsers hand to the state store. DEL-009What a 200 promises the device.

DEL-010What the portal tells users. DEL-011The firmware relationship — including saying no to "just require firmware X".

The one firmware ask

  • A firmware change takes 12–18 months to spread, and never reaches every device.
  • So we ask for something that improves a feature, never something a feature depends on.
  • The ask: when a device carries out a command, it reports back that command's id.
  • On devices that get it, Inferred and Unknown become Confirmed.
  • We build the inference anyway, and keep it for the devices that never update.

DEL-012Report the command id back on the next sync — one string, stored and sent back.

DEL-013Inferred from the expected change, shipped regardless, and kept permanently.
